# ADR-0001: Unified MCP Router Pattern (Single Tool, Action Dispatch)

**Status**: Accepted  
**Date**: 2025-07-14  
**Context**: Initial architecture decision for scholaris-mcp

---

## Context

When designing the MCP server interface, two structural approaches were considered:

**Option A — Multiple MCP tools**: Register `review_paper`, `check_venue_fit`,
`diff_audit`, and `generate_rebuttal` as separate MCP tools, each with their own
input schemas.

**Option B — Single unified tool with `action` parameter**: Register one `scholaris`
tool whose Zod schema encompasses all actions, dispatching internally based on
the `action` parameter value.

The forgecraft-mcp project uses Option B (the scholaris-router pattern is adapted
from forgecraft-router). This project follows the same pattern for consistency
and because it has the same advantages.

---

## Decision

Adopt Option B: one MCP tool (`scholaris`), one Zod schema, one `dispatch()` function.

---

## Rationale

1. **Single schema = single source of truth**: All parameter names, types, optional/required
   rules, and descriptions live in one place (`scholaris-router.ts`). Adding a parameter
   never requires updating two tool registration records.

2. **Testability**: The entire tool contract is exercised through `dispatch()`. The router
   is the integration test boundary — no need for MCP transport layer in tests.

3. **Claude tool-use ergonomics**: Claude interacts with one tool that has clear
   `action` enumeration. The enum descriptions serve as inline documentation visible
   to the model at call time.

4. **Reduced MCP server surface**: One tool registration vs. four reduces the risk of
   tool-list pollution and makes the server easier to reason about.

---

## Consequences

- The `scholaris-router.ts` schema must be updated when any handler adds a new parameter.
  This is acceptable — the router is explicitly the API contract.
- All new actions follow the pattern: Zod schema → handler function → test file.
  No exceptions (see CLAUDE.md MCP Tool Contract).
- Parameters shared across actions (e.g. `paper_text`) are optional at the schema level
  and validated with `requireParam()` inside handlers that need them.

---

## Rejected Alternative

Option A was rejected because it would scatter the API contract across 4 registration
calls, making it harder to maintain consistent parameter naming conventions and
harder to write tests that exercise the full dispatch path.
