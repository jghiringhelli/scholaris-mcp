# ADR-0002: YAML Templates for Venue and Review Profile Knowledge

**Status**: Accepted  
**Date**: 2025-07-14  
**Context**: Initial architecture decision for scholaris-mcp

---

## Context

The domain knowledge for academic venues (what NeurIPS requires, how Nature differs from
IEEE, etc.) and review profiles (which logical fallacies to check, what rhetorical prompts
to apply) must be stored somewhere. Two approaches were considered:

**Option A — TypeScript hardcoding**: Define venue and profile configurations directly
as TypeScript objects or constants in source files.

**Option B — YAML template files**: Store all domain knowledge as data files in
`templates/venues/` and `templates/review-profiles/`, loaded at runtime by the registry.

---

## Decision

Adopt Option B: YAML files in `templates/`, loaded by `src/registry/loader.ts`.

---

## Rationale

1. **Non-developers can contribute domain knowledge**: A researcher who wants to add
   support for EMNLP or CVPR can write a YAML file without modifying TypeScript source.
   The schema is documented in CLAUDE.md and is simple enough for non-engineers.

2. **YAML is the right semantics for declarative configuration**: Venue criteria, rejection
   patterns, and review prompts are data, not behavior. Encoding them as TypeScript
   conflates the concerns of "what to check" with "how to check".

3. **Separation of knowledge from logic**: The review engine (renderers, handlers) has
   no opinion about what NeurIPS requires. The NeurIPS template does. This boundary
   enables swapping, extending, or versioning venue/profile definitions independently
   of the engine.

4. **Template drift is visible as data changes, not code changes**: When ICML updates
   its requirements, the change is a YAML diff — a clean semantic unit reviewable by
   domain experts, not a code reviewer.

5. **Testing templates independently of the engine**: Template loading tests validate
   YAML structure separately from handler behavior tests.

---

## Consequences

- `loader.ts` owns the runtime YAML → TypeScript type bridge. Type safety is enforced
  by treating loaded data as `unknown` and casting — a deliberate trade-off. A Zod
  schema on YAML loading would be ideal for future hardening.
- Template files must follow the schema in CLAUDE.md exactly. Runtime errors from
  malformed templates will be thrown as `TemplateLoadError`.
- Adding a new venue or profile requires a YAML file AND type registration
  (VenueId / ReviewProfileId union in types.ts + Zod enum in router). This is documented
  in CLAUDE.md as the standard procedure.
- The `TEMPLATES_DIR` path uses `fileURLToPath(import.meta.url)` to be resolution-safe
  in both `src/` (ts-node) and `dist/` (compiled) contexts. This is tested in the
  loader integration tests.

---

## Rejected Alternative

Option A was rejected because it would make every venue or profile update a code change,
requiring compilation, tests, and a versioned release. It would also prevent domain experts
who are not TypeScript developers from contributing venue definitions.
